# طريقة الاختبار الجديدة — قسم الصيانة

## لماذا تغيرت الطريقة؟
الهاتف لم يعد يحلل ملف DWG أثناء فتح الصفحة. التحليل أصبح عملية بناء مسبقة على GitHub Actions، ثم تُحفظ النتيجة كبيانات ثابتة داخل `data/feeders/`.

هذا يمنع مشاكل `content://` و`Failed to fetch` ويجعل صفحة الجوال سريعة.

## التشغيل
1. ارفع جميع ملفات المشروع إلى المستودع.
2. افتح GitHub ثم تبويب **Actions**.
3. شغّل **Build feeder database** يدويًا من **Run workflow** إذا لم يبدأ تلقائيًا.
4. انتظر حتى تصبح المهمة خضراء.
5. افتح GitHub Pages.
6. افتح **مواقع المغذيات**.
7. افتح **بيانات الرسم** لرؤية الملفات الخام الناتجة.

## الملفات الناتجة
- `manifest.json` — ملخص وعدادات القراءة.
- `stations.json` — أسماء المحطات المرشحة والمثبتة حرفيًا من الرسم.
- `feeders.json` — المغذيات مع سياق المحطة إن أمكن إثباته.
- `all_text_entities.json` — كل النصوص الهندسية.
- `all_feeder_candidates.json` — النصوص المرشحة كمغذيات.
- `layers.json` — جميع Layers.
- `blocks.json` — جميع Blocks وعدد الكيانات داخلها.
- `entity_types.json` — أنواع الكيانات وأعدادها.
- `database_tables.json` — جداول DWG المهمة.
- `raw_database.json` — قاعدة DWG المحولة كاملة مع معالجة BigInt والدورات المرجعية.
- `full_analysis.json` — تقرير تحليلي مجمع.
- `drawing.svg` — محاولة تحويل الرسم إلى SVG.

## قاعدة الدقة
لا يتم إنشاء أسماء مثل `SUB1` أو `SUB2` من النظام. أي اسم محطة أو مغذي يظهر للمستخدم مأخوذ حرفيًا من النص المقروء من الرسم. إذا لم يمكن إثبات علاقة محطة بمغذي، تبقى العلاقة `unresolved` بدل اختراعها.

## الخطوة التالية
بعد نجاح البناء وثبوت المحطات والمغذيات، سيتم ربط كل سجل مغذي بقاعدة مواقع المعدات وإظهار معدات المغذي وإحداثياتها والخريطة، ثم تخصيص الرسم لكل مغذي قدر الإمكان من بنية الرسم.
